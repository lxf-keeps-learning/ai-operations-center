# 报告分析记录降级展示设计

## 背景

报告分析页通过 SSE 生成报告，再通过 `/operation/records` 刷新历史记录。当前两条流程相互独立：报告生成成功后，历史记录刷新失败会直接显示“系统内部错误”，并且左侧列表为空，但中间报告内容仍然存在，造成页面状态不一致。

## 目标

- 报告生成成功后立即在左侧“分析记录”展示该报告。
- 历史记录刷新失败不清空已生成报告，也不显示阻塞式整页错误。
- 历史记录刷新成功后，用服务端记录替换临时记录，避免重复项。
- 保持现有报告预览、下载和追问能力不变。

## 设计

### 临时记录

页面增加一个仅存在于当前页面生命周期的临时记录状态。SSE `report_completed` 转换为 `OperationResult` 后，根据结果中的 `record_id`、当前筛选条件、报告摘要和生成时间构造列表项，并置于真实记录列表之前。临时项使用稳定的临时 key，直到服务端返回同一 `record_id` 的真实记录。

临时记录不写入数据库，不参与跨页面缓存；刷新页面后仍以服务端记录为准。

### 刷新与替换

报告生成完成后继续调用 `fetchRecords()`。成功时：

1. 更新服务端记录列表。
2. 如果返回了对应 `record_id`，删除临时记录。
3. 如果服务端暂时未返回对应记录，保留临时记录，避免报告刚生成时因事务提交延迟再次变成空列表。

失败时：

1. 保留临时记录和当前报告预览。
2. 将错误降级为列表区域内的非阻塞提示，例如“历史记录暂时无法刷新，当前报告仍可查看”。
3. 不把该错误合并到页面顶部的生成错误中。

### 选择与预览

临时记录可被点击。点击后优先展示当前已生成的内存报告；如果临时记录已有 `record_id`，则尝试请求详情，详情请求失败时保留当前报告预览并提示详情暂不可用。

真实记录刷新成功后，选中状态按 `record_id` 迁移到真实记录，保证用户不需要重新点击。

## 备选方案与取舍

- 仅隐藏历史接口错误：改动最小，但左侧仍为空，无法明确告诉用户报告已生成。
- 只修复后端 `/operation/records`：能解决数据库或接口异常，但无法覆盖网络失败、服务重启和提交延迟等情况。
- 临时记录 + 后台刷新（采用）：同时解决当前状态错乱和短暂外部失败，改动集中在页面状态层，不改变数据库契约。

## 错误处理

- 生成流程错误仍显示在现有生成失败区域。
- 历史列表加载错误显示在列表区域，并保留已有记录与临时记录。
- 详情加载错误不覆盖已存在的生成结果。

## 测试策略

- 为记录合并/替换逻辑增加前端可测试的纯函数测试：临时记录置顶、服务端记录命中后替换、未命中时保留。
- 为页面状态增加回归测试或最小组件测试：生成结果存在且列表刷新失败时，报告仍可见且错误为非阻塞提示。
- 运行前端类型检查和生产构建；运行后端现有测试，确认接口契约未受影响。

## 成功标准

1. 生成报告成功后，左侧立即出现对应报告记录。
2. `/operation/records` 失败时，不出现截图中的整页“系统内部错误”，中间报告仍可查看。
3. 记录接口恢复后，临时记录不会与真实记录重复。
4. 前端 `type-check` 和 `build` 通过。
