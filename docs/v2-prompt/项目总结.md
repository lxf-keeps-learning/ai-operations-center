# AIOperationsCenter V2 Prompt 管理中心项目总结

> 总结日期：2026-07-28
> 总结范围：以 V2 Prompt 管理中心为主，说明它如何接入现有 AIOperationsCenter 运营分析链路。
> 结论口径：以下结论来自当前代码、自动化测试、数据库迁移和本地页面验收，不把未联网验证的能力描述为已生产落地。

## 1. 项目定位

AIOperationsCenter 是面向智能运营中心（IOC）的 AI Agent 项目。V1 已具备运营分析 Graph、Tool Center、报告追问、RAG、SSE 事件流和本地审计能力；V2 在此基础上新增“AI 策略与 Prompt 管理中心”，解决 Prompt 长期硬编码、修改风险高、版本不可追踪和效果难评估的问题。

V2 的核心不是做一个文本编辑器，而是把 Prompt 变成可治理的运行资产：

```text
业务规则编辑
→ 草稿版本
→ 最终 Prompt 预览
→ 测试与基础评估
→ 提交审核
→ 正式发布
→ LangGraph 读取生产版本
→ Trace 记录 Prompt 事实
→ 指标观察与失败案例沉淀
→ 必要时回滚
```

当前选取 `ioc.safety.analysis` 作为首个接入场景，对应 Operation Graph 的 `analyze_reason` 节点。

## 2. 要解决的核心问题

### 2.1 Prompt 与业务代码耦合

原有节点从本地文件读取 Prompt。业务规则调整需要改代码、走部署，运营人员也难以确认最终发给模型的内容。

V2 将 Prompt 拆成以下层次：

- System Prompt：系统角色、安全边界和不可覆盖约束。
- Business Prompt：业务目标、规则、输出要求、正反例。
- Runtime Context：设备、指标、告警、历史数据和证据。
- User Question：本次用户问题。

运营侧主要维护业务层，系统层、模型配置和输出 Schema 仍由技术侧控制。

### 2.2 “最新版本”不能等于“生产版本”

生产 Graph 不能直接读取最新草稿。系统通过 `prompt_release` 维护环境发布记录，运行时按 `prompt_key + environment` 解析已发布版本；版本内容发布后不可直接编辑，只能复制为新草稿。

### 2.3 修改效果缺少证据

系统补充了单条测试、测试用例、确定性评估、指标页、版本对比、实验和失败案例模块。当前第一期重点是完成可运行闭环，复杂 A/B 流量和在线 LLM Judge 仍属于后续生产化工作。

### 2.4 调用问题难追溯

`analyze_reason` 节点会把 `prompt_key`、`prompt_version`、`prompt_commit_hash` 和环境写入 Graph State、LLM usage 及 LangSmith metadata 合并路径，使“哪次调用使用了哪个 Prompt”具备可追踪基础。

## 3. 当前实现架构

```text
Vue 3 Prompt 管理页面
  ├─ 列表 / 详情 / 业务视图
  ├─ 编辑 / 预览 / 测试 / 对比
  ├─ 审核 / 发布 / 回滚
  └─ 指标 / 评估 / 实验 / 失败案例
                │ REST
                ▼
FastAPI V2 Modules
  ├─ prompt_center
  ├─ evaluation_center
  ├─ experiment_center
  └─ failure_center
                │
                ▼
SQLAlchemy + Alembic
  ├─ Prompt 定义、版本、变量、发布、审计
  ├─ 测试用例、测试运行、评估结果
  ├─ 实验与版本结果
  └─ 失败案例
                │
                ▼
Operation Graph / analyze_reason
  ├─ 读取 production 已发布版本
  ├─ 注入 Runtime Context
  ├─ 失败时回退原有本地 Prompt
  └─ 写入 Prompt Facts 与 Trace Metadata
                │ 发布前（可选严格模式）
                ▼
LangSmith Prompt Hub
  ├─ private ChatPromptTemplate
  ├─ Commit Hash + Version Tag
  └─ 同步失败不切换 active release
```

后端仍沿用现有统一响应、错误码、Trace Context、数据库基类和模块注册方式，没有另建一套基础框架。

## 5. 关键技术实现

### 5.1 不可变版本与状态机

Prompt 定义与 Prompt 版本分表保存。核心状态包括：

```text
draft → reviewing → approved → published
             └────→ rejected
published → rollback
```

发布服务会校验版本属于当前 Prompt，避免跨 Prompt 发布；预览、测试和版本对比也增加了同类完整性校验。

### 5.2 生产环境按发布记录读取

`render_prompt` 在 production 环境优先读取当前 active release，而不是取“最新版本”。这保证运营人员创建草稿或审核中的版本不会直接影响线上 Graph。

### 5.3 可回退的 LangGraph 接入

`analyze_reason` 节点调用统一 Prompt 集成层：

- 正常情况：读取 `ioc.safety.analysis` 的 production 版本。
- 管理中心或数据库不可用：回退到原有 `system_prompt.md` 和 `operation_analysis.md`。
- 调用完成：记录 Prompt Key、Version、Commit 和 Environment。

这一设计控制了改造风险，避免 Prompt 管理中心故障直接中断既有运营分析流程。

### 5.4 预览与真实运行边界

真实运行必须校验必填变量；静态预览允许变量暂缺，并显示 `<未提供：变量名称>`。这样既不降低生产校验强度，也避免运营人员仅查看最终 Prompt 时被运行时变量阻断。

### 5.5 评估与实验

确定性评估用于检查 JSON、字段完整性、枚举、证据和禁止项等可程序化规则；语义评估保留 LLM-as-a-Judge 扩展接口。实验中心按用户选择的版本和测试用例执行，并以实际执行结果计算样本数。

### 6.2 本地页面闭环

使用最新迁移创建一次性 SQLite 验收库，并以种子 Prompt 完成：

1. 列表读取 `ioc.safety.analysis`。
2. 查看业务详情和动态变量。
3. 修改业务目标并创建 `v1.1.0` 草稿。
4. 提交审核并审核通过。
5. 发布到 production。
6. 在发布历史中确认新版本。
7. 回滚到上一版本。
8. 查看最终 Prompt 预览。
9. 查看测试变量输入、质量指标、评估、实验和失败案例页面。

验收过程中发现并修复了迁移链、Vite 代理优先级、预览请求契约、必填变量静态预览、前端测试变量初始化等集成问题。

## 7. 项目价值与评估方式

当前没有生产流量和长期运营数据，因此不宣称已经实现确定的降本比例。建议在试点阶段用以下指标验证：

| 目标 | 指标或公式 |
|---|---|
| 缩短 Prompt 变更周期 | `从提出变更到生产发布的平均时长` |
| 降低发布风险 | `回滚次数 / 发布次数`、发布后 P1/P2 问题数 |
| 提升输出质量 | `通过的评估项 / 总评估项 × 100%` |
| 降低人工返工 | `需人工重写的报告数 / 总报告数` |
| 控制成本 | 单次平均 Token、平均延迟、单次模型成本 |
| 提升可追溯性 | 可关联 Prompt Version 的模型调用占比 |

建议用一组固定数据集对比“硬编码旧版本”和“管理中心发布版本”，至少观察 2～4 周，再形成业务收益结论。

## 8. 当前边界

- 本轮未调用真实外部 LLM，单条测试验证到页面、API、持久化和 Mock/自动化边界。
- 已实现 LangSmith Prompt Hub 自动同步代码，但本轮只使用 Fake Client 验证，没有上传真实 Prompt、请求、模型输出或业务数据；远程账号端到端仍待隔离环境验收。
- 当前身份字段和审核动作具备审计基础，但未接入企业 SSO、网关 RBAC 和租户级授权。
- MySQL 是目标数据库；本轮 V2 迁移使用一次性 SQLite 从既有基线版本升级验证，未在生产 MySQL 执行。
- 灰度发布接口与数据结构已预留，但自动流量分配、复杂 A/B、多模型自动比较未完成。
- 指标页当前展示本地测试/评估数据，尚无生产样本和线上质量基线。
- 运行时只将 `analyze_reason` 作为首个托管节点，并非所有 Graph 节点都已迁移。
- 前端构建存在大 chunk 警告，暂不影响功能验收。

## 9. 下一步建议

1. 在隔离测试项目中开启严格同步，使用脱敏 Prompt 完成真实 Commit、Tag 和脱敏 Trace 上传验收。
2. 接入企业身份与 RBAC，将编辑、审核和发布职责真正分离。
3. 在 MySQL 测试环境执行完整升级、回滚和数据兼容验证。
4. 建立固定 Dataset，补充真实模型回归和 LLM Judge 校准。
5. 接入线上失败采集，形成失败案例 → 测试用例 → 新版本实验的闭环。
6. 为灰度发布补充真实路由、样本量门槛、显著性判断和自动停止规则。
7. 按业务优先级逐步托管更多 LangGraph 节点。
