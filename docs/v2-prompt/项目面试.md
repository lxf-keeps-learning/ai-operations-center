# AIOperationsCenter V2 Prompt 管理中心项目面试

> 使用原则：只讲当前代码和本轮验收能证明的内容。涉及生产收益、远程 LangSmith、真实模型效果和企业权限时，要主动说明验证边界。

## 1. 一句话介绍

我在 AIOperationsCenter 原有运营分析 Agent 上增加了一个 AI 策略与 Prompt 管理中心，把硬编码 Prompt 改造成可分层编辑、版本管理、测试评估、审核发布、生产读取和快速回滚的运行资产。

## 2. 30 秒介绍

这个项目面向企业智能运营中心，原有系统用 LangGraph 编排运营分析、Tool Center 获取 KPI 和告警数据，并生成可追问的分析报告。V2 主要解决 Prompt 治理问题：我将 Prompt 拆成系统层、业务层、运行时上下文和用户问题，建立草稿、审核、发布和回滚流程；生产 Graph 只读取 production 已发布版本，并把 Prompt Key、Version、Commit 和环境写入 State 与 Trace Metadata。当前通过 436 个后端测试、前端类型检查和构建、迁移校验，以及一次完整页面发布回滚闭环。

## 3. 1 分钟介绍

项目原来已经能生成运营分析报告，但核心 Prompt 仍主要跟代码一起维护，存在三个问题：业务规则调整必须发版、线上到底用了哪个 Prompt 不好追溯、修改后缺少测试和回滚机制。

我在不推翻原有架构的前提下新增四个后端模块：Prompt、Evaluation、Experiment 和 Failure Center；前端增加列表、详情、编辑、测试、对比、审核发布、指标等页面。Prompt 定义与不可变版本分离，运行时按环境发布记录读取，不取最新草稿。首个接入点是 `ioc.safety.analysis`，对应 `analyze_reason` 节点；管理中心异常时仍可回退原来的本地 Prompt。

本轮本地验收真实完成了创建 `v1.1.0` 草稿、提交审核、审核通过、production 发布和回滚。远程 LangSmith 上传、真实模型效果、企业 RBAC 和自动灰度还没有做生产验收，我会把这些作为下一阶段，而不是包装成已完成。

## 4. 3 分钟介绍

### 4.1 背景

AIOperationsCenter 用 LangGraph 编排运营分析，通过 Tool Center 获取结构化业务数据，再由规则和 LLM 完成异常识别、原因分析、建议生成与报告汇总。V1 已有 Report Chat、RAG、SSE 和审计能力，但 Prompt 还是偏研发资产。

### 4.2 我的目标

我的目标不是简单加一个 Prompt 文本框，而是建立最小可用治理闭环：

```text
编辑业务规则
→ 创建不可变草稿版本
→ 预览和测试
→ 审核
→ 发布到指定环境
→ Graph 读取已发布版本
→ 记录 Prompt 事实
→ 观察指标
→ 出问题时回滚
```

### 4.3 核心设计

第一，把 System Prompt 和 Business Prompt 分开。运营人员可调整业务目标、规则和表达要求，但系统安全约束、模型配置与 Schema 仍受保护。

第二，把“版本”和“发布”分开。版本描述内容快照，发布记录描述哪个版本在哪个环境生效。因此 production 不会误读草稿。

第三，采用渐进式接入。`analyze_reason` 先读取托管 Prompt，同时保留本地文件回退，避免管理中心不可用时破坏原有 Graph。

第四，建立可观测事实。节点把 Prompt Key、Version、Commit 和 Environment 写入 State、LLM usage 和 LangSmith metadata 合并路径。

第五，评估分层。格式、字段、枚举等由确定性 Evaluator 检查；回答相关性、是否虚构和建议可执行性为 LLM Judge 预留接口。

### 4.4 验收结果

当前后端全量 436 个测试通过，前端类型检查和生产构建通过，Alembic 为单一 Head；本地页面完成草稿、审核、发布和回滚。真实模型和远程 LangSmith 没有在本轮发送数据，因此效果指标仍需试点验证。

## 5. 架构怎么讲

### Q1：整体链路是什么？

前端通过 REST 调用 FastAPI。Prompt Center 负责定义、版本、变量、发布和审计；Evaluation Center 负责评估结果和指标；Experiment Center 负责版本对比；Failure Center 负责失败案例沉淀。生产 Operation Graph 在 `analyze_reason` 节点通过集成层读取 production 发布版本，把运行时数据作为变量注入，调用 LLM 后记录 Prompt Facts。

### Q2：为什么不直接接 LangSmith Prompt Hub？

IOC 需要业务字段、角色权限、审核、发布、回滚和本地审计，这些不是单纯 Prompt Hub 能完整表达的。我的划分是：

- IOC：业务管理入口和发布控制面。
- LangSmith：Prompt Commit、Trace、Evaluator、Dataset 和 Experiment 的底层平台。

当前本地管理闭环已完成，但远程 Commit/Tag 和真实 Trace 上传尚未验收。

### Q3：为什么要分四层 Prompt？

因为不同内容的责任和生命周期不同：

- System：安全边界和技术协议，低频、受保护。
- Business：业务规则，高频、可运营。
- Runtime Context：每次请求动态注入。
- User Question：当前用户意图。

如果全部混在一个文本框里，既容易越权覆盖系统约束，也无法清楚审计“改了什么”。

## 6. 版本与发布深挖

### Q4：为什么版本表和发布表要分开？

一个版本可以在 testing、staging、production 等不同环境生效，且发布还需要记录发布类型、发布人、审核人、说明和回滚关系。把两者分开后：

- `prompt_version` 表示不可变内容快照。
- `prompt_release` 表示环境指针和发布事实。

回滚本质上是让环境重新指向上一有效版本，并新增一条 rollback 记录，而不是修改历史版本内容。

### Q5：如何保证线上不用到草稿？

`render_prompt` 在 production 环境查询 active release，再取其 `version_id`。创建新草稿不会改变 active release。发布服务还会校验版本状态和 Prompt 归属。

### Q6：版本号怎么生成？

仓储层根据当前版本序列生成下一个版本。第一版是 `1.0.0`，后续草稿按当前策略递增次版本，如 `1.1.0`。重点不只是字符串，而是版本内容不可变、发布记录可追踪。

### Q7：如何防止跨 Prompt 发布错误版本？

发布、预览、测试和对比都会检查 `version.prompt_id == prompt_id`。本轮专门增加了跨 Prompt 发布失败的回归测试。

## 7. LangGraph 与可靠性

### Q8：如何接入现有 LangGraph？

我没有让 Node 直接依赖 Repository，而是通过 `get_rendered_prompt` 集成函数读取统一 `PromptRenderResult`。Node 只负责准备运行时变量、取出 system/user message、调用 LLM 和记录事实。

### Q9：Prompt 管理中心挂了，Graph 会不会挂？

不会直接中断。接入层支持 fallback messages，仍可使用原来的本地 `system_prompt.md` 和 `operation_analysis.md`。这样可先在单个节点试点，再逐步扩大托管范围。

### Q10：为什么生产环境不能取最新版本？

“最新”只说明创建时间，不说明它已经测试、审核或适合生产。生产读取 release，是为了让变更经过显式决策，并保留快速回滚能力。

### Q11：怎么知道某次模型调用用了哪个 Prompt？

节点记录：

```json
{
  "prompt_key": "ioc.safety.analysis",
  "prompt_version": "1.0.0",
  "prompt_commit_hash": null,
  "prompt_environment": "production"
}
```

这些事实写入 Graph State 和 LLM usage，并合并到 LangSmith metadata 路径。Commit 为空表示尚未完成远程 Prompt Commit，不伪造值。

## 8. 预览、测试与评估

### Q12：预览和真实运行有什么区别？

真实运行必须校验必填变量，否则应明确失败；静态预览主要帮助运营人员理解最终 Prompt，因此允许变量暂缺，并显示 `<未提供：设备名称>` 这类标记。两者不能共用完全相同的宽松策略。

### Q13：单条测试做了什么？

用户选择版本、填写问题和动态变量，后端拼装测试 Prompt、调用模型、保存原始输出、结构化输出、Token、延迟和 Trace，再查询评估结果。当前本轮没有调用真实外部模型，真实质量需在隔离测试环境补验。

### Q14：为什么不能只用字符串匹配做 Prompt 遵守率？

字符串匹配适合检查明确字段或禁词，不适合判断是否回答问题、是否虚构、建议是否可执行。因此分两层：

- 确定性：JSON、Schema、必填字段、枚举和禁止项。
- 语义性：相关性、证据性、无虚构和建议质量。

最终遵守率可计算为：

```text
通过的评估次数 / 总评估次数 × 100%
```

### Q15：如何做 A/B 实验才可信？

至少要保证相同数据集、相同模型参数、明确评价指标和足够样本。当前实验模块已能绑定源版本、目标版本和选定测试用例，并按实际执行结果统计样本；自动灰度流量、显著性检验和真实模型实验仍未完成。

## 9. 数据库与迁移

### Q16：核心表有哪些？

- `prompt_definition`：Prompt 业务身份和当前状态。
- `prompt_version`：不可变内容版本。
- `prompt_variable`：运行时变量定义。
- `prompt_release`：环境发布与回滚记录。
- `prompt_test_case` / `prompt_test_run`：测试资产和执行结果。
- `prompt_evaluation` / `evaluation_result`：评估结果。
- `prompt_audit_log`：关键操作审计。
- `prompt_experiment` / `experiment_result`：版本实验。
- `failure_case`：线上失败案例。

### Q17：如何验证迁移？

## 10. 验收中最有价值的排障案例

### STAR 1：页面列表一直是空数据

**Situation：** 后端临时数据库已有种子 Prompt，接口也返回 200，但前端显示 0 条。
**Task：** 判断是数据库、API 契约、状态管理还是代理问题。
**Action：** 先核对 SQLite 数据，再分别读取 8011 后端响应和 5180 代理响应，最终发现 Vite 配置只读取 `.env`，忽略启动命令中的代理地址，页面实际连接到另一个 8000 服务。随后调整为进程环境变量优先。
**Result：** 页面正确显示 `ioc.safety.analysis`，并完成后续发布闭环。

### STAR 2：创建版本成功但页面没有反馈

**Situation：** 点击创建版本后，数据库已生成 `v1.1.0`，页面却停留在编辑页。
**Task：** 找到“后端成功、前端仍失败”的第二阶段错误。
**Action：** 查看后端访问日志，发现版本创建返回 200，紧接着预览接口返回 422。根因是前端发送 `version`，后端却复用了要求 `prompt_key` 的 RenderRequest；项目其实已有 PreviewRequest 但路由未使用。统一改为 `version_id` 契约并新增 API 回归测试。
**Result：** 预览接口恢复，回归测试覆盖请求契约。

### STAR 3：静态预览被必填变量阻断

**Situation：** 详情页切到完整视图时，因为没有 `device_name` 和 `realtime_data` 返回 400。
**Task：** 在不降低生产变量校验的情况下让预览可用。
**Action：** 区分 preview 与 runtime：生产渲染继续严格校验；预览优先使用示例值、默认值，仍缺少时填入醒目标记。
**Result：** 最终 Prompt 可查看，同时真实运行仍保持严格校验。

### STAR 4：实验页在旧临时库报字段不存在

**Situation：** 扩展页首次冒烟时，ORM 查询 `test_case_ids` 报 SQLite 列不存在。
**Task：** 判断是迁移代码缺陷还是验收环境漂移。
**Action：** 检查发现临时库创建时间早于字段加入；没有手工改库掩盖问题，而是用当前迁移重新从基线创建干净数据库，并确认表结构和页面 API。
**Result：** 实验列表返回 200，也证明当前 V2 迁移能生成完整 Schema。

可用公式：

```text
Prompt 遵守率 = 通过评估项 / 总评估项 × 100%
人工返工率 = 需人工重写报告数 / 总报告数
发布回滚率 = 回滚次数 / 发布次数
版本可追溯率 = 带 Prompt Version 的模型调用数 / 总模型调用数
```

## 13. 高频质疑

### Q21：“这不就是一个 Prompt CRUD 吗？”

不是。CRUD 只解决保存问题，这个项目还解决了职责分层、不可变版本、状态流转、环境发布、生产版本解析、Graph 接入、Trace 事实、测试评估和回滚。真正的难点在运行时一致性和治理闭环。

### Q22：“为什么不让运营人员直接改完整 Prompt？”

因为 System Prompt 包含安全约束、工具协议和输出 Schema。完全开放会引入 Prompt Injection、结构破坏和越权风险。运营人员应在明确的业务字段范围内编辑，技术字段受保护。

### Q23：“有了回滚为什么还要测试和审核？”

回滚只能降低故障恢复时间，不能避免错误影响用户。测试和审核负责降低发生概率，回滚负责降低影响时间，两者职责不同。

### Q24：“LangSmith 已经接好了吗？”

准确回答是：本地已经实现 Prompt Commit/Tag 字段、Trace metadata 合并和后端封装基础，自动化测试验证 metadata 路径；本轮没有使用真实账号上传业务 Trace，也没有完成远程 Prompt Commit 的端到端验收。

### Q25：“已经能自动灰度和 A/B 吗？”

目前有灰度发布、实验和结果模型的基础结构，但没有真实流量路由、自动停止规则和统计显著性判断，所以不能说成完整在线 A/B 平台。
